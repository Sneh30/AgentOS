Webcmd slots in as a second execution backend under your existing browser layer — not a replacement for Composio, a complement to it. Here's the mapping onto gtm-os as it stands:

| gtm-os piece | What webcmd adds |
|---|---|
| `src/lib/browser.ts` (Firecrawl search/scrape) | Firecrawl is generic/unauthenticated. Webcmd's `linkedin` and `twitter` adapters are authenticated, structured, and site-specific — `webcmd linkedin posts` / `webcmd linkedin search` returns clean JSON instead of an LLM parsing scraped markdown. Your exact example — "find LinkedIn posts mentioning our product" — is one deterministic webcmd call, not a browser-agent loop. |
| `gtm-toolkits.ts` allowlist | Extend it to cover two auth families: Composio-OAuth toolkits (CRM, email, calendar) and webcmd-browser-profile toolkits (`linkedin`, `twitter`). Same gating logic — a site not in the allowlist never gets registered as a tool, same as today. |
| `tools-enhanced.ts` registry | On `initializeTools()`, run `webcmd list -f json`, filter to allowlisted sites, and register each command as a tool (`webcmd:linkedin:search`, etc.) with an auto-built zod schema from webcmd's arg metadata. They plug into `getRegisteredTools(policy)` exactly like built-ins do. |
| `executor-enhanced.ts` dispatch | Add a third branch next to built-in/Composio: name starts with `webcmd:` → shell out to the CLI, parse `-f json`, feed into `formatStepResult()`. Failures go into `executionHistory` and replan, same as everything else. |
| Agent Library (`gtm_agents.toolkits`) | An agent's `toolkits` array can now mix `LINKEDIN` (Composio) and `webcmd:linkedin` (browser) — e.g. a "LinkedIn Mention Finder" template scoped to `webcmd:linkedin` only, since it needs read/search, not the write-heavy Composio actions. |
| Auth / `AuthConnectionCard` | Different flow, same card shape conceptually — Composio auth is an OAuth redirect URL; webcmd auth is "log into this site in the Webcmd browser profile, then `webcmd doctor` goes green." Worth flagging: this only works where gtm-os has local browser access, which is exactly the case for Anymind AgentOS as an Electron desktop app — webcmd is a poor fit for a purely hosted web deployment but a strong fit for the desktop shell you're already building. |
| `hydra.ts` knowledge store | Webcmd's sitemap-memory layer (layer 2 — recorded navigation knowledge per site) is a natural sibling to `storeKnowledge()`. You could pipe captured sitemaps into the same HydraDB knowledge collection so an agent recalls both "what I scraped" and "how this site's navigation works" from one place. |
| Cost/reliability story | This is the actual payoff, not just a feature add: today every scheduled agent run re-plans and re-scrapes from scratch. Webcmd's CLI layer is deterministic — a daily "check LinkedIn mentions" agent stops burning planner tokens on navigation every single run. |

**Thin first slice, if you want to ship something real fast:** don't build the auto-registration pipeline yet. Hardcode `webcmd:linkedin:search` and `webcmd:linkedin:posts` as two new built-in tools (same pattern as `browser_search`/`browser_scrape`), add `webcmd:linkedin` to the allowlist, and make the LinkedIn Mention Finder template use it. That validates the whole loop — CLI shell-out → JSON → `formatStepResult` → agent run — before you invest in dynamically registering webcmd's full adapter catalog.

One thing to decide before wiring further: do you want webcmd to *replace* Composio's LinkedIn toolkit, or run alongside it (Composio for anything transactional/OAuth-friendly, webcmd for read-heavy feed/search stuff Composio's LinkedIn scope doesn't cover)? That decision changes whether `LINKEDIN` and `webcmd:linkedin` coexist as two entries or you drop one.
